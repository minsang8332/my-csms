# SDD 가이드 및 표준

본 문서는 **스펙 주도 개발(Spec-Driven Development, SDD)** 및 **검수(Verification)** 표준 구조와 가이드라인을 정의한다.

---

## 1. 스펙 문서 디렉토리 구조

스펙 문서는 **기능 계획 및 설계 문서(`plans/`)**와 **검수 명세 문서(`verifications/`)**를 상위 폴더로 명확히 구분하여 관리한다.

```
specs/
├── README.md                          # SDD 개발 및 검수 표준 가이드 (본 문서)
├── templates/                         # 스펙 작성용 표준 템플릿
│   ├── FEATURE_SPEC_TEMPLATE.md       # 신규 기능 개발 스펙 템플릿
│   ├── REFACTOR_SPEC_TEMPLATE.md      # 아키텍처 변경 및 리팩토링 스펙 템플릿
│   └── VERIFICATION_SPEC_TEMPLATE.md  # 검수 시나리오 및 결과 보고 템플릿
├── plans/                             # [기능 계획] 기능 및 아키텍처 설계 스펙 (SPEC-XXX)
│   └── {domain}/
│       └── SPEC-XXX-{feature}.md
└── verifications/                     # [검수 명세] 검수 시나리오 및 결과 문서 (VERIFY-XXX)
    └── {domain}/
        └── VERIFY-XXX-{feature}.md
```

### 1.1 관리 책임과 조회 방법

- `README.md`는 작성 규칙과 작업 절차만 관리한다.
- 스펙의 상태와 내용은 각 `SPEC` 또는 `VERIFY` 문서가 유일한 원본이다.
- 별도의 수동 색인 문서는 두지 않는다. 전체 목록은 `rg --files specs/plans specs/verifications`로 조회한다.
- 상태 변경 시 원본 문서만 수정하며, 별도 목록이나 상태 집계를 동기화하지 않는다.

---

## 2. 스펙 문서 작성 및 명명 규칙

스펙 문서 작성 및 관리는 아래의 통합 작성 규칙을 준수한다.

### 2.1 파일 경로 및 문서 ID 표준

- **기능 계획 스펙 (SPEC)**: `specs/plans/{도메인명}/SPEC-{일련번호}-{기능명}.md`
- **검수 명세 스펙 (VERIFY)**: `specs/verifications/{도메인명}/VERIFY-{일련번호}-{기능명}.md`

### 2.2 표기법 및 언어 규칙

- **케밥 케이스(kebab-case) 사용**: 파일명과 도메인명은 소문자 영문과 하이픈(`-`)만을 조합하여 작성한다.
- **용어 혼용 및 명확성**: 코드 식별자, API 엔드포인트, 설정 키 등은 영문 원어를 유지하고, 요구사항 설명 및 배경은 한국어 기본 문체(`~한다`, `~이다`)로 작성한다.

### 2.3 일련번호 할당 기준

- 번호는 도메인과 관계없이 `001`부터 3자리 전역 순번으로 부여한다.
- 새 번호는 기존 `SPEC-XXX` 중 가장 큰 번호의 다음 번호를 사용한다.
- 하나의 개발 스펙과 대응하는 검수 문서는 같은 번호를 사용한다. 예: `SPEC-001` ↔ `VERIFY-001`.
- 도메인과 작업 성격은 번호가 아닌 디렉토리와 파일명으로 구분한다.

### 2.4 스펙 작성 기본 원칙

1. **요구사항 타당성 검토 (Feasibility Review & Constructive Critique)**:
   사용자 및 개발 요구사항에 대한 무조건적인 수용은 엄격히 금지한다. 더 나은 프로그램과 안정적인 아키텍처를 위해 보안성, 성능, 유지보수성, 기존 시스템 영향도에 대한 **타당성 검토를 반드시 선행**해야 한다. 비효율적이거나 위험 요소가 있는 요청은 합리적인 대안을 제시하고 논의를 통해 스펙에 반영한다.
2. **단일 진실 공급원 (Single Source of Truth)**: 모든 개발 및 아키텍처 사양은 `specs/` 하위 문서가 최신 기준이다.
3. **추적성 (Traceability)**: `specs/verifications/` 하위의 검수 스펙(`VERIFY-XXX`)은 `specs/plans/` 하위의 개발 스펙(`SPEC-XXX`)과 1:1로 대응하며 추적 가능해야 한다.
4. **검증 가능성 (Verifiability)**: 요구사항과 합격 기준은 주관적 표현을 지양하고 측정 가능한 수치 또는 명확한 동작 시나리오로 명시한다.
5. **코드 동기화 (Synchronization)**: 개발 도중 설계 변경이 발생하면 스펙 문서를 먼저 수정한 후 코드를 구현한다.
6. **데이터 보존 (Data Preservation)**: 기존 DB 데이터를 초기화·전체 삭제·덮어쓰기하여 복구하기 어렵게 만드는 요청과 작업은 거부한다. `prisma migrate reset`, `db push --force-reset`, `DROP`/`TRUNCATE`, 조건 없는 대량 삭제, Docker DB 볼륨 또는 `csms-db/data` 삭제, 기존 DB를 덮어쓰는 복원 작업을 포함한다. 이러한 작업이 필요해 보이는 경우에도 실행하지 않고, 백업 후 비파괴적 마이그레이션이나 별도의 격리된 DB 사용 등 데이터가 보존되는 대안을 제시한다.

### 2.5 스펙 작성 판단 기준

다음 중 하나에 해당하면 스펙을 작성한다.

- 신규 기능이나 사용자 동작을 추가 또는 변경하는 작업
- API, 데이터 모델, 시스템 구조 또는 배포 방식이 변경되는 작업
- 여러 모듈에 영향을 주거나 보안·데이터 손실 위험이 있는 작업
- 구현 전에 대안 비교와 사용자 승인이 필요한 작업

다음 작업은 별도 스펙 없이 구현하고 변경 결과만 보고할 수 있다.

- 오탈자, 문서 정리, 사용하지 않는 코드 제거
- 동작을 바꾸지 않는 국소적인 리팩토링
- 원인이 명확하고 영향 범위가 작은 버그 수정
- 개발 도구나 관리 절차의 단순 정비

## 3. 스펙 라이프사이클

개발 스펙은 아래 7가지 상태 단계에 따라 관리된다.

```
 [Draft] ──► [In Review] ──► [Approved] ──► [Development] ──► [Verification] ──► [Implemented] ──► [Deprecated]
```

| 상태             | 설명                                                                     |
| ---------------- | ------------------------------------------------------------------------ |
| **Draft**        | 스펙 초안을 작성 중인 상태 (개발 착수 불가)                              |
| **In Review**    | 스펙 작성 완료 후 검토 및 피드백을 받는 상태                             |
| **Approved**     | 스펙 검토 및 승인이 완료되어 개발을 시작할 수 있는 상태                  |
| **Development**  | 승인된 스펙에 따라 코드를 구현 중인 상태                                 |
| **Verification** | 코드 구현 완료 후 검수 명세서(`VERIFY-XXX`)에 따라 검증을 진행 중인 상태 |
| **Implemented**  | 검수 결과 통과(PASS) 후 최종 승인되어 코드베이스에 적용이 완료된 상태    |
| **Deprecated**   | 더 이상 사용되지 않거나 새로운 스펙으로 대체된 상태                      |

검수 문서는 `Draft → Verification → Pass | Fail` 상태로 관리한다. `Fail`이면 개발 스펙을 `Development`로 되돌려 보완하고 다시 검수한다.

## 4. 검수 가이드라인

검수 명세서(`specs/verifications/{도메인}/VERIFY-{일련번호}-{도메인명}.md`)는 **구현된 기능이 개발 스펙(`SPEC-XXX`)의 요구사항에 맞게 작동하는지 검증하고 기록하는 문서**이다.

### 4.1 필수 검수 항목

1. **기능 검수**: 주요 정상 흐름과 예외 흐름 동작 검증
2. **사이드이펙트 검수**: 기존 시스템 영향 및 예외 처리, 성능, 자원 사용량, 보안 차단 동작 검증
3. **자동화 테스트**: 단위/통합 테스트 및 CLI 명령어 실행 결과 검증

### 4.2 검수 판정 기준

- **PASS (합격)**: 모든 필수 검수 항목을 통과하고 부작용이 없는 경우
- **FAIL (불합격)**: 필수 기능 오류, 예외 미처리, 보안 문제 등이 발생한 경우 (재작업 필요)

---

## 5. 작업 흐름

1. **작성 필요성 판단**: 2.5 기준에 따라 별도 스펙이 필요한 작업인지 먼저 판단한다.
2. **기능 계획 스펙 작성**: 필요한 경우 `FEATURE_SPEC_TEMPLATE.md` 또는 `REFACTOR_SPEC_TEMPLATE.md`를 복사하여 `plans/{도메인}/SPEC-{번호}-{기능명}.md`를 작성한다.
3. **검토 및 승인**: 타당성 검토 후 상태를 `In Review`로 변경하고, 사용자 승인 시 `Approved`로 변경한다.
4. **구현 및 검수 준비**: 구현 시작 시 개발 스펙을 `Development`로 변경하고, 같은 번호의 `VERIFY` 문서를 작성한다.
5. **검수 진행**: 구현 완료 후 두 문서의 상태를 `Verification`으로 변경하고 검수 시나리오를 수행한다.
6. **최종 완료**: 검수 문서를 `Pass`, 개발 스펙을 `Implemented`로 변경한다. 실패하면 각각 `Fail`, `Development`로 변경한다.
